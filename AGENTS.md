# AGENTS.md

## Project
**Nestro** — VS Code extension (`src/extension.ts`) managing npm/pnpm/yarn/bun packages from the sidebar with update status and version switching. Built on the VS Code Extension API (`@types/vscode 1.125.0`). Update detection uses `npm-check-updates` (dynamically imported in `src/utils/ncuClient.ts`).

## Commands
Core dev/test loop; the full script table (all scripts, non-mutating gate flags) is the single
source of truth in **[CONTRIBUTING.md](CONTRIBUTING.md)** → Commands.

```bash
pnpm run build            # tsdown → out/extension.cjs
pnpm run dev              # tsdown --watch
pnpm run lint             # eslint src --max-warnings=0 — non-mutating validation gate
pnpm run lint:fix         # eslint --fix src — the mutating pass, never run automatically
pnpm run typecheck        # tsc --noEmit
pnpm run test:compile     # tsc -p tsconfig.test.json → out/test/
pnpm run test:minimum     # vscode-test --label minimum — Extension Host on VS Code 1.125.0
pnpm run test:stable      # vscode-test --label stable — Extension Host on the stable channel
pnpm run test:unit        # vitest run — *.unit.test.ts without VS Code
pnpm run test:unit:watch  # vitest (watch mode)
```

Integration tests: `.vscode-test.mjs` runs the `minimum` and `stable` channels against every
`out/test/**/*.test.js`; no single-file isolation, and the two channels must not run concurrently
against the same checkout — each resets its own channel directories on load.
Unit tests: Vitest, `vscode` mocked via `src/test/__mocks__/vscode.ts`. Shared helpers live in
`src/test/fixtures/`; its `index.ts` barrel is also loaded by the Extension Host suites, so helpers
that import `vitest` (`providerStub.ts`, `workspaceFs.ts`, `auditProcess.ts`, `config.ts`) are
imported from their own files, not through the barrel.
Manual testing: **F5** → Run Extension (`.vscode/launch.json`) → Extension Development Host window.

## Architecture

### Data flow
1. `activate()` creates `FilterManager` and `PackagesProvider`, then calls `provider.loadPackages()`.
2. `loadPackages()` delegates to `PackageLoadingService.load()` (`src/providers/packageLoadingService.ts`), which reads workspace `package.json` files via `readAllWorkspaceDependencies()` (`src/utils/packageReader.ts`, backed by `packageRepository.ts` file I/O and `packageTransforms.ts` parsing) and resolves each file's canonical location (`src/providers/packageLocationResolution.ts`) → populates `PackageRowStore.allEntries: PackageTreeEntry[]`.
   A rejected reload clears those rows and publishes an actionable load-error row linked to the
   status report; because the failure is recorded, `nestro.noWorkspace` stays false. `WorkspaceCapabilityResolver`
   resolves global action flags and probes Yarn family outside `runWithYarnFamilyMemo()`, preserving the existing
   uncached call behavior. `getStatusReport()` delegates defensive snapshot assembly to `statusReportAssembler.ts`.
3. `checkUpdates()` delegates to `UpdateOrchestrationService.check()` (`src/providers/updateOrchestrationService.ts`), which calls `fetchAllLatestVersions()` (ncuClient → `npm-check-updates`) and the metadata registry → enriches each entry with the accepted version, `updateType`, and release-age state (`accepted`, `held-back`, or `unknown`), preserving any live `installing` state set by `markPackageUpdating()`. Update results are cached to avoid redundant network calls.
4. `getChildren()` delegates to `buildTree()` (`src/providers/treeBuilder.ts`) which returns `GroupItem[]` (or `WorkspaceFolderItem[]` when the workspace has more than one `package.json`) — groups split into Dependencies / Dev Dependencies. The active filter/search state renders as `treeView.description` (`formatViewDescription()`), not as tree rows.
5. Commands mutate provider state via `markPackageUpdating()` / `markPackageUpdated()` / `resetUpdateData()` / `invalidateUpdateCache()`, then fire `_onDidChangeTreeData`. The state-only `markPackageUpdating()` / `markPackageUpdated()` methods take an exact `PackageStateIdentity` tuple `(packageName, packageFilePath, section)`; package-row commands use provider-issued `ResolvedPackageItem` capabilities through `markPackageUpdatingForCapability()` / `markPackageUpdatedForCapability()`, which reject stale capabilities.

### Key patterns

**Write suppression** — When a command writes to `package.json` (e.g. updating a version), it calls `provider.withWriteSuppressed(fn)`. The provider captures SHA-256 digests for tracked manifests immediately before and after `fn` and records a baseline only for files whose digest changed; successful writes also invalidate the update cache. At debounce, the watcher asks the provider whether each changed manifest still matches its baseline; a missing baseline, unreadable file, or different digest triggers a reload. Unchanged manifests keep their baselines, so nested or overlapping calls do not clear another write's baseline.

**Workspace folder watcher** — `registerWorkspaceFoldersWatcher()` (`src/extension.ts`) listens to `vscode.workspace.onDidChangeWorkspaceFolders`; on change it refreshes the package.json watcher and calls `provider.loadPackages()` so packages stay in sync when workspace folders are added or removed.

**Package manager detection** — `ClientManager.detectPackageManager(cwd)` in `src/clients/ClientManager.ts` walks up ancestor directories to the workspace folder, checking the `packageManager` field and then lockfiles (pnpm-lock.yaml → yarn.lock → bun.lock → package-lock.json) at each level; undefined `cwd` returns `npm`. `updateOrchestrationService.ts` and `pickVersion.ts` inject this detector into `metadataRegistry`.

**Deferred install mode** — When `nestro.deferInstallAfterUpdate` is enabled, single updates write through `updateDependencyVersionsInFile()` and Update All writes atomically through `updateDependencyVersionsInFilesAtomically()` without running a package manager install. The user then runs `nestro.runInstall` separately.

**Per-click debounce** — `checkUpdates()` enforces a debounce via `nestro.checkUpdatesDebounce` (seconds), but only when the update cache is still valid for the current `updateTarget` / `includePreReleases` / package-file set; a config or package-set change bypasses the debounce. Set `nestro.checkUpdatesForceAlways` to `true` to bypass the debounce and always run immediately. `invalidateUpdateCache()` clears both the cache and the last-check timestamp. `checkUpdates()` also no-ops if a check is already `running`, preventing concurrent update checks from overlapping. `runAudit()` follows the same pattern, no-oping if `auditState` is already `running`. Applying a fetched result is gated separately by a content fingerprint over every dependency's canonical path, section, name and on-disk spec plus the update policy: the fingerprint is recomputed from disk immediately before the cache write, and a mismatch discards the whole fetch instead of caching it.

**Provider operation lifecycle** — `loadPackages()`, `checkUpdates()` and `runAudit()` use `OperationLifecycle<T>` for generation ownership, abort signals, progress cancellation and completion. Update checks and audits wait for the current package load before reading rows. If discovery fails without finding package files, the next explicit check or audit retries the load first. A progress token already cancelled before its task starts cancels that run before it can reach the update or audit service.

**Context variables** — `emitTreeChanged()` publishes every key in `CONTEXT_KEYS` (`src/shared/ids.ts`, aliased `VIEW_CONTEXT_KEYS` in `src/providers/viewProjectionService.ts`) for `when`/`enablement` clauses in `package.json`; the non-obvious ones:
- `nestro.canUpdateVisiblePackages` — true when filtered list has outdated packages (controls "Update All" button)
- `nestro.noWorkspace` — true only after loading settles with no discovered package files and no package-file read failures (shows welcome content; an empty manifest still counts as a workspace)
- `nestro.hasSearchQuery` — true when the active search query is non-empty (controls the Clear Search Query overflow entry); reset to `false` on `dispose()`

`PackageItem.contextValue` starts with `package` or `outdated`, or `installing-<operation>`, and may append `pinnable` / `pin-unsupported` and `vulnerable-<severity>` tokens. The inline update menu uses `viewItem =~ /(^|-)outdated($|-)/` to match the outdated token despite suffixes; other row actions use base-prefix or capability-token regexes.

### Providers (`src/providers/`)
- `PackagesProvider.ts` — thin `TreeDataProvider` + `Disposable` facade; preserves the command and extension API while delegating state, row capabilities, row mutations, load/update/audit operations, workspace capability resolution, tree projection, context publication, and status-report assembly to focused siblings
- `packageProviderState.ts` — owns the shared package snapshot, operation status, capability records, row store, package item construction, and cached owner-qualified labels from `packageLabels.ts`
- `packageCapabilityOperations.ts` — resolves and revalidates provider-issued package capabilities at command boundaries
- `packageRowMutationService.ts` — marks package rows updated or installing while preserving capability freshness and progress-race recovery
- `packageLoadController.ts` — applies package-loading snapshots, resolves workspace action capabilities, and owns load cancellation and failure state
- `packageUpdateController.ts` — runs update checks through `UpdateOrchestrationService`, applies current results, and owns update cancellation and status
- `packageAuditController.ts` — runs audits through `AuditOrchestrationService`, applies report snapshots and row badges, and owns audit cancellation and status
- `packageViewController.ts` — builds tree/status items and publishes tree-view state and context keys; package detail file paths come from the shared `packageLabels.ts` resolver
- `workspaceCapabilityResolver.ts` — resolves workspace action flags and checks auditable project support, including the Yarn family probe
- `statusReportAssembler.ts` — builds defensive status-report snapshots and package read/update failure entries
- `packageRowStore.ts` — `PackageRowStore` owns `allEntries`; `patchRow()` and `restoreAt()` record row mutations through `PackageCapabilityService.noteRowMutation()`, while `replaceAll()` applies snapshot and presentation rebuilds
- `packageLabels.ts` — the single owner-qualified and relative package-file label builder used by tree rows, package rows, details, status reports, and Update All messages
- `packageLabelPaths.ts` — normalizes package paths for labels across POSIX, drive, and UNC forms and sanitizes path text
- `packageLabelDisambiguation.ts` — assigns stable workspace display names and unique label suffixes
- `FilterManager.ts` — manages active `FilterType` and search state, fires `onDidChange`, provides QuickPick UI, and reads filter icon colors from `PACKAGE_PRESENTATION`
- `treeBuilder.ts` — pure package-tree filtering, grouping, projection, and item construction; delegates owner and relative package-file labels to `packageLabels.ts`. Multi-root file rows preserve `WorkspaceFolder.index` ordering, root before subpaths, and alphabetical order within a folder. `getFilterCounts()` excludes packages currently installing; `formatViewDescription()` renders the active filter/search state for `treeView.description`.
- `auditOrchestrationService.ts` — `AuditOrchestrationService.run()` wraps project resolution and audit work in one `runWithYarnFamilyMemo()` scope, resolves audit projects via `clients` (`resolveAuditProjects()`), runs each project's package-manager audit (`auditProjectRunner.ts`), and folds the per-project outcomes into the `AuditProjectSummary` / `AuditProjectFailure` results `runAudit()` publishes; row attribution lives in `auditRowAttribution.ts` (a row takes the highest severity among its attributed advisories, matching versions through `auditVersionMatching.ts`), and for npm audit report v2, whose advisories carry no version field, `auditInstalledVersion.ts` resolves the installed version from an advisory's single direct `node_modules/<name>` node (`parseDirectNodeModulesNode()`) through a bounded reader (`readNodePackageJsonVersion()`) gated by a realpath-inside-project-root check, leaving anything ambiguous report-only
- `operationLifecycle.ts` — `OperationLifecycle<T>` owns one operation's generation, `AbortController`, completion and progress cancellation (including a token cancelled before the task starts); load/update/audit controllers keep one each, and `waitForCurrent()` lets checks and audits wait for the current load
- `packageLoadingService.ts` — `PackageLoadingService.load()` reads workspace `package.json` files and resolves each one's canonical on-disk location into a `PackageLoadingSnapshot` (entries, package file paths, read failures) that `loadPackages()` applies to `PackageRowStore.allEntries`
- `manifestWriteBaselines.ts` — `ManifestWriteBaselines` compares SHA-256 snapshots around provider writes and keeps a baseline only for a manifest the write changed, dropping it once the file's digest no longer matches
- `updateOrchestrationService.ts` — `UpdateOrchestrationService.check()` wraps a complete check in `runWithYarnFamilyMemo()` and coordinates cache/debounce and fingerprint reuse; exports `computeUpdateFingerprint()` for the content-fingerprint gate described in Key patterns
- `updateOrchestrationTypes.ts` — update orchestration contracts and result types, re-exported by `updateOrchestrationService.ts` to preserve its public API
- `updateFingerprint.ts` — computes the content fingerprint from canonical manifest paths, on-disk dependency specs, and update policy
- `updateCheckFetcher.ts` — resolves canonical coordinator keys, fetches per-manifest latest versions, and reports unresolved roots as explicit per-root failures
- `updateMetadataFetcher.ts` — resolves registry keys and fetches release-date metadata for unique (registry, package) pairs, bounded only by the metadata coordinator
- `updateReleaseAge.ts` — classifies the accepted version's release age from the metadata outcomes and current version
- `updateCache.ts` — owns the cache record, policy key, TTL freshness, and debounce decision
- `updateResultApplication.ts` — rechecks the fingerprint and current policy before applying results, rejects stale or invalidated fetches, and updates the cache
- `viewProjectionService.ts` — `computeViewProjection()` owns the context-key map, badge, `treeView.description`, and filtered `PackageTreeProjection`; `diffViewContexts()` reduces two context maps to changed keys. Pure: no VS Code events, `setContext` calls, or `TreeItem` construction. It delegates ordered status-row construction to `statusRowProjection.ts`.
- `statusRowProjection.ts` — builds package-read, update, audit, filter, and search status rows in display order from the provider snapshot
- `capabilityService.ts` — `PackageCapabilityService` issues the frozen `ResolvedPackageItem` capabilities and decides freshness: a capability stays valid while the snapshot generation, the row's mutation count (`noteRowMutation()`, recorded by `PackageRowStore.patchRow()` and `restoreAt()`) and its manifest spec (`currentVersion`, `versionPrefix`) are unchanged, so an audit, update check, or settings reset that rebuilds the `PackageItem` objects does not invalidate a command in flight
- `packageIdentity.ts` — canonical row identity shared by the loading, update, and audit services: `packageIdentityKey()` is the single row identity-key builder; `packageIdentityFromValues()` creates the exact `(name, packageFilePath, section)` tuple, and dependency specs are read from one manifest parse
- `packageLocationResolution.ts` — `resolveCanonicalPackageLocation()` validates manifest paths against the unique deepest workspace owner; `samePackageFileStamp()` checks whether a manifest still matches its captured stat identity
- `PackageItem.ts` — defines the package tree row, normalizes active operations, and guards command arguments with `isPackageItem()`
- `packageItemPresentation.ts` — builds package row descriptions, tooltips, context values, icons, accessibility labels, release-age text, fallback workspace labels, and sanitized package text
- `PackageDetailItem.ts`, `GroupItem.ts`, `StatusItem.ts`, `LoadingItem.ts`, `MessageItem.ts`, `WorkspaceFolderItem.ts` — other tree item classes
- `index.ts` — barrel exports for providers

### Clients (`src/clients/`)
- `PackageManagerClient.ts` — the single client, constructed with a `PackageManager` and driven by its `PACKAGE_MANAGERS` row; `buildUpdateCommand()` / `buildInstallCommand()` / `buildRemoveCommand()` return a `ShellTaskCommand` (`src/utils/shellTask.ts`) rather than a raw string, and `runAuditReport()` dispatches to the manager's audit runner. The one private `buildArgv()` validates every operand via `operandValidation.ts` (an invalid operand throws before a task is ever built), shell-quotes it as a `vscode.ShellQuotedString` (`ShellQuoting.Strong`) and puts it after a `--` separator, with the section flag (`--save-dev` / `--dev`) and the workspace-root flag before it, so a package name can never be parsed as a CLI option; an update whose targets span both dependency sections throws instead of moving a prod dependency into dev
- `operandValidation.ts` — `validatePackageName()` / `validatePackageVersionSpec()`; the localized error messages over `classifyPackageName()` (`src/shared/packageName.ts`, the vscode-free name classifier the metadata clients share) and `isVersionOperand()`; rejects only what makes an operand option-like or unresolvable (leading hyphen, empty name, malformed scope, URL-unsafe characters) — mixed case and length past 214 pass as real legacy registry names, leading `.`/`_` pass only because they're inert operands, not real ones
- `ClientManager.ts` — creates the `PackageManagerClient` for the detected package manager; `detectPackageManager(cwd)` walks ancestor directories up to the workspace folder
- `projectResolver.ts` — `resolveAuditProjects()` groups discovered `package.json` files into canonical audit projects by real project root and owning workspace folder, merging manifests that share one lock-file graph and rejecting workspace escapes/collisions; `resolveMutationCoordinatorKey()` derives the same canonical root as the `OperationCoordinator` lock key and rejects, rather than issuing a raw key, when a canonical path cannot be resolved
- `lockfileDetection.ts` — `findLockfile()` finds the first lock file in `LOCKFILES` order in a directory (optionally for one manager) with `vscode.workspace.fs.stat`, never reading the file
- `canonicalWorkspaceFolders.ts` — `resolveCanonicalOwningWorkspaceFolder()` matches a canonical directory to its deepest owning workspace folder; `withCanonicalWorkspaceFolderScope()` shares each folder's `realpath` (batched, bounded) between all calls made while any scope is open, so a bulk operation canonicalizes the folders once
- `workspaceRoot.ts` — `isWorkspaceRoot()` tells `ClientManager.getClient()` whether the task directory is a workspace root where `add` (and, under Yarn Classic, `remove`) is refused without the table's `workspaceRootFlag`: a `pnpm-workspace.yaml` listing two or more `packages` globs for pnpm (a single glob needs no flag), a `workspaces` manifest field under Yarn Classic (`resolveYarnFamily()`; Yarn Modern rejects the flag); `PackageManagerClient` places the flag only for such a client, so a child package never gets it
- `index.ts` — barrel exports for clients

### Commands (`src/commands/`)
- `copyPackageName.ts` — `copyPackageNameCommand`; copies the row's package name to the clipboard via `vscode.env.clipboard.writeText()`; guarded by `isPackageItem()`, logs and no-ops on an invalid argument
- `installUpdate.ts` — `installUpdateCommand`, `updateAllVisibleCommand`; update commands use the shared `runRowMutation()` pipeline, and a single update is represented as a batch of one. Immediate package-manager runs use cancellable VS Code shell-task progress through `runShellTaskAndWait()` (`src/utils/shellTask.ts`); typed cancellation clears row progress and reconciles package state without an error toast, while Update All reports partial cancellation as information. Successful updates invalidate the update cache and record each version through the capability-based provider API; non-zero or missing exit codes show `formatShellTaskFailureMessage()`. Update All confirms before proceeding and locks all affected project roots together. Deferred single updates use the single-manifest writer; deferred batches use the atomic multi-manifest writer, with each capability's explicit dependency `section`. `resolvePackageFileLabels()` (`src/providers/packageLabels.ts`) supplies the same owner-qualified labels and ordering as the tree, avoiding false prefix matches between similarly named workspace folders (e.g. `app` vs `app-mobile`)
- `packageUpdateExecution.ts` — groups immediate updates by manifest, revalidates package capabilities before each task, marks rows during cancellable package-manager runs, and formats partial failures and cancellations with the tree's owner-qualified manifest labels
- `runInstall.ts` — `runInstallCommand` chooses a workspace manifest, locks its project, marks its rows by exact `PackageStateIdentity`, runs the package-manager task with cancellable progress, and clears marks after completion or cancellation
- `openAuditReport.ts` — `openAuditReportCommand`; renders the latest audit snapshot (`provider.getAuditReport()`) through `formatAuditReport()` into the shared output channel and shows it
- `openOnNpm.ts` — `openOnNpmCommand`; opens `https://www.npmjs.com/package/<name>` via `vscode.env.openExternal()`; guarded by `isPackageItem()`
- `openStatusReport.ts` — `openStatusReportCommand`; renders `provider.getStatusReport()` through `formatStatusReport()` into the shared output channel and shows it
- `pickVersion.ts` — `pickVersionCommand`; shows QuickPick for selecting a specific package version; disposes the QuickPick and its listeners on hide so a version fetch resolving after the user cancels does not act on a stale picker
- `pinAllVersions.ts` — `pinAllVersionsCommand`; runs through `runRowMutation()` while holding the locks for all workspace manifests, then pins versions through the shared atomic multi-file write/rollback in `packageReader.ts` (preflights every file before the first write; a manifest that fails to parse is skipped and named in the result message by its `resolvePackageFileLabels()` tree label rather than aborting the whole run); marks and clears manifest rows by exact `PackageStateIdentity`; invalidates the update cache and reloads packages on failure too, since a rolled-back write may still have touched disk, but skips the reload when nothing needed pinning
- `pinVersion.ts` — `pinVersionCommand`; runs through `runRowMutation()` and toggles supported concrete dependency specs between exact and caret versions in the selected dependency section, preserving the `workspace:` protocol; stale row capabilities stop before the write
- `removePackage.ts` — `removePackageCommand`; confirms before locking, then runs the package manager remove command through cancellable `runShellTaskAndWait()` progress under `runRowMutation()`; invalidates the update cache after the task; success, non-zero or missing exits, and user cancellation reload packages, with cancellation clearing row progress and logging without an error toast
- `switchDepType.ts` — `switchDepTypeCommand`; runs through `runRowMutation()` to move a dependency between `dependencies` and `devDependencies`; a target-section collision is reported without writing, and a completed write clears progress and reloads packages
- `packageIdentity.ts` — shared command-side identity resolution: `resolveCommandPackageItem()` / `revalidateCommandPackageItem()` re-check a row against the provider immediately before a write or task; `resolveManifestEntry(item, provider, otherSectionDuplicate)` reads through `readPackageFile()` and `parsePackageJson()`, with `reject` for removal and `allow` for pinning; not re-exported through `index.ts` — commands import it directly as a subsystem sibling
- `rowMutation.ts` — `runRowMutation()` owns the guard → resolve → canonical coordinator locks → revalidate → mark → apply → reconcile order for row-mutating commands; partial capability marks are cleared through the provider, and a coordinator-key rejection goes to the command's own `reportError` before any row is marked
- `packageUpdateSteps.ts` — update-only steps shared by the single and batch update flows: post-task verification and completion marking, per-manifest grouping, single vs atomic multi-manifest deferred writes, failed-batch reconciliation, the Update All confirmation, and the unverified / partial-failure messages
- `updateRiskConfirmation.ts` — confirms held-back package updates before a package-manager task and remembers the accepted package/version identities for the current update run

### Utils (`src/utils/`)
- `ncuClient.ts` — thin wrapper around `npm-check-updates` (dynamic `import('npm-check-updates')` to avoid bundling issues); caches the imported `run()` function and returns `Map<name, latestVersion>`; `UpdateOrchestrationService` owns the update-result cache
- `metadataRunner.ts` — runs one bounded HTTPS request with timeout, cancellation, and a response-byte cap; classifies transport, timeout, cancellation, truncation, and overflow outcomes, then delegates completed responses to `metadataResponse.ts`; defaults to a 15s timeout and 5MiB response limit
- `metadataResponse.ts` — classifies completed HTTP responses by content length and status, parses JSON, maps schema results, and builds typed transport errors
- `metadataRegistry.ts` — resolves package-manager-aware metadata adapters in tier order (native CLI, config-aware HTTPS), exposes a credential-free resolved-registry key for bounded deduplication, and uses native CLI for npm/pnpm and both Yarn family commands before the config-aware HTTPS fallback
- `releaseAge.ts` — classifies versions against the minimum release-age setting (validated by `readMinimumReleaseAgeDays()` in `shared`) using absolute UTC publish instants
- `metadata/` — `packument.ts` (`parsePackument()`, the one packument parser for CLI and HTTPS: versions newest first, dist-tags, optional publish times) and `cliAdapter.ts` (the one CLI adapter: package-name validation before any spawn, the `--json -- <name>` argv from the package-manager table, bounded run and process-outcome mapping)
- `nativeMetadataClient.ts` — runs bounded `npm view` / `pnpm view` requests from the package root, runs them through the shared CLI adapter, and maps process outcomes to the metadata taxonomy
- `yarnMetadataClient.ts` — runs bounded Yarn Classic and Modern metadata commands after `resolveYarnFamily()` selects the matching command shape, wraps the shared packument parser per family, and maps process outcomes to the metadata taxonomy
- `yarnFamily.ts` — `resolveYarnFamily()` picks Yarn Classic vs Modern for one project root: explicit `packageManager` metadata first, then same-root markers, then a bounded `yarn --version` probe as last resort; nothing defaults to Classic. `runWithYarnFamilyMemo()` resolves each root once within an operation scope; calls outside that scope remain uncached
- `envExpansion.ts` — `expandEnvironmentReferences()`, the single environment-reference expansion; each config format passes its own `EnvSyntax` (`NPM_ENV_SYNTAX`: `${NAME}` kept literal when unset, `${NAME?}` empty; `YARN_CLASSIC_ENV_SYNTAX` and `BUN_ENV_SYNTAX`: unset rejected; `YARN_MODERN_ENV_SYNTAX`: `${NAME}`, `${NAME-fallback}`, `${NAME:-fallback}`, anything else starting `${` rejected); returns `undefined` for a rejected reference and never echoes a variable value
- `bunConfig.ts` — parses the supported `bunfig.toml` registry and scope forms, expanding environment references and normalizing URL-embedded credentials; quoted strings and inline tables come from `bunTomlValues.ts`
- `bunTomlValues.ts` — parses Bun TOML quoted strings and inline registry tables, including environment expansion and supported escapes
- `registryClient.ts` — the config-aware HTTPS metadata adapter's entry points: `fetchPackageMetadataFromRegistry()` / `resolvePackageRegistryUrl()` compose the `registry/*` modules below, mark private-registry outcomes, and parse versions, dist-tags and optional publish times (`parseNpmRegistryMetadata()`); also `selectVersionsForPicker()`
- `registry/` — the config-aware adapter's parts, each one concern: `configFiles.ts` (the single config-path builder, home directory then workspace root down to the package, and the one any-error-to-`undefined` file read), `configValues.ts` (quote unwrapping), `npmrc.ts` (`.npmrc` and `npm_config_*` parsing, key normalization, `@scope:registry` and `//host/:_authToken` keys), `packageScope.ts` (the single package-scope rule: `@scope/name` with a non-empty scope), `miniYaml.ts` (the YAML subset Yarn Modern uses), `yarnrc.ts` (Yarn Classic `.yarnrc`), `yarnrcYml.ts` (Yarn Modern `.yarnrc.yml` keys and scopes), `yarnConfiguration.ts` (reads and merges the Yarn files of the resolved Yarn family), `bunConfiguration.ts` (reads and merges `bunfig.toml`), `configResolution.ts` (`resolveRegistryConfiguration()` merges npm, Yarn and Bun sources into one `RegistryConfiguration`), `configSourceMemo.ts` (`runWithRegistryConfigMemo()` caches npm, Bun and Yarn configuration sources per package file for one update check), `tls.ts` (`ca` / `cafile` / `caFilePath` resolution and `strict-ssl`), `proxy.ts` (`NO_PROXY` rules), `auth.ts` (`getAuthorizationHeader()`), `registryUrl.ts` (HTTPS-only registry and packument URLs), `httpClient.ts` (bounded requests with redirect handling that drops credentials across origins)
- `audit/types.ts` — the one audit severity model: `AuditSeverity`, `AuditPackageManager`, `AuditSchemaId`, the worst-to-least `SEVERITY_ORDER`, `compareSeverity()` / `mergeSeverity()` / `parseSeverity()`, `YARN_CLASSIC_SEVERITY_BITS` (Yarn Classic exit-code mask) and `emptySeverityCounts()`; imports nothing, so `audit/outcome.ts` and `auditReport.ts` share it without an import cycle
- `audit/outcome.ts` — the one audit outcome pipeline: the `AuditOutcome` / `AuditResult` types and `UnrecognizedAuditResultError`; `runAuditCommand()` runs one bounded audit process and maps every non-exit runner outcome (`describeBoundedProcessFailure()`); `readAuditJsonDocument()` is the shared exit-code / empty / JSON preamble; `buildRecognizedOutcome()` is the one clean-or-advisories builder; `toAuditResult()` narrows a recognized outcome. Each client only parses its own schema
- `audit/fields.ts` — advisory field readers shared by the schema parsers: `isAdvisoryId()` and `parseFixAvailable()`
- `auditClient.ts` — runs `npm audit` / `pnpm audit` and parses the npm v1/v2 report schemas into an `AuditResult`'s advisories through the shared `audit/outcome.ts` pipeline; row attribution onto `PackageItem` badges happens in `auditOrchestrationService.ts`, not here
- `auditReport.ts` — shared audit advisory model: `createAuditAdvisory()` / `mergeAuditAdvisories()`, direct/transitive/unknown attribution merging, and text sanitization used by every audit client and the report formatter
- `auditReportFormatter.ts` — `formatAuditReport()` renders the `openAuditReport` output-channel text from `AuditProjectSummary` / `AuditProjectFailure`; `validateAdvisoryUrl()` guards advisory links before they're shown
- `bunAuditClient.ts` — `runBunAudit()` runs Bun's raw-registry bulk-advisory JSON audit contract (schema `bun-bulk-advisory`) and parses it through the shared `audit/outcome.ts` pipeline
- `yarnAuditClient.ts` — `runYarnAudit()` selects the Yarn Classic or Modern command with `resolveYarnFamily()` and normalizes each family's schema into the shared `AuditResult`; it delegates Classic parsing to `yarnClassicAudit.ts` and shares line parsing from `yarnAuditParsing.ts`, while Modern validates its npm-audit tree output and expected exit code
- `yarnAuditParsing.ts` — parses JSON output lines and identifies malformed-line failures shared by the Yarn Classic and Modern audit parsers
- `yarnClassicAudit.ts` — parses Yarn Classic audit records, verifies the final summary counts, and requires an exit code equal to the severity mask
- `processRunner.ts` — `runBoundedProcess()` spawns and supervises a child process, classifying outcomes as `exit`, `timeout`, `overflow`, `aborted`, or `spawn-error`; delegates capped stream capture to `boundedOutput.ts` and process-tree termination to `processTermination.ts`; launches commands through `resolveSpawnTarget()` (`src/shared/spawnTarget.ts`); shared by the native/Yarn/Bun metadata and audit runners
- `boundedOutput.ts` — `BoundedOutput` counts stdout and stderr bytes independently, retains chunks up to the cap, and drops the chunk that crosses it
- `processTermination.ts` — `ProcessTerminator` sends a graceful process-tree termination, then escalates to a forceful kill after the configured grace period; uses `taskkill.exe` on Windows
- `shellTask.ts` — `runShellTaskAndWait()` runs a `vscode.Task` via `vscode.tasks.executeTask()` using a `ShellTaskCommand` (`{ command, args }`, each shell-quoted via `vscode.ShellQuotedString`), shows cancellable notification progress titled with the task name, and resolves a `ShellTaskOutcome` — `ended` with the process exit code (or `undefined` when the task reports none) or `cancelled`; cancellation terminates the execution and settles without waiting for end events, and every outcome disposes listeners. Shared by `runInstall.ts`, `installUpdate.ts`, and `removePackage.ts`; `formatShellTaskCommandForLog()` renders a command for logs, and `formatShellTaskFailureMessage()` formats real failures
- `packageReader.ts` — reads workspace `package.json` dependencies; `updateDependencyVersionsInFile()` takes an explicit `DependencySection` (`dependencies` | `devDependencies`) per update rather than inferring it; preserves the original indentation style (spaces or tabs) when rewriting `package.json`
- `packageRepository.ts` — file I/O for workspace `package.json` files: `findWorkspacePackageJsonFiles()`, `readPackageFile()`, and the atomic `writePreparedPackageFile()` / `writeManyPreparedPackageFilesAtomically()` writers `packageReader.ts` builds on
- `packageTransforms.ts` — pure `package.json` document transforms: `parsePackageJson()` / `serializePackageJson()` and the `prepare*()` / `transform*()` functions that compute a dependency-type switch, version pin, or bulk pin-all-versions edit without touching disk
- `dependencySpec.ts` — parses a dependency's version spec into range (`exact` / `caret` / `tilde`) and protocol (`plain` / `workspace`), flagging specs the pin toggle must leave untouched with a user-facing reason
- `operationCoordinator.ts` — `OperationCoordinator` serializes mutations by canonical project-root key, running different keys concurrently up to a `concurrencyCap`; acquires multi-key locks in sorted order to stay deadlock-free
- `rootOperation.ts` — `startRootOperations()` / `runRootOperations()` run bounded per-root work over an `OperationCoordinator`, separating prompt cancellation from actual settlement so a cancelled operation still releases its coordinator slot
- `statusReport.ts` — `formatStatusReport()` renders the `openStatusReport` output-channel text from a `StatusReportSnapshot` (read/update/audit failures, file labels), sanitizing file URIs, absolute paths, and credential-shaped text out of the output
- `localization.ts` — `vscode.l10n.t()`-backed label formatters (`formatUpdateTypeLabel()`, `formatAuditSeverityLabel()`, `formatDependencySectionLabel()`, package-count/advisory-row phrasing) shared by the tree, status report, and audit report; also the `Intl`-backed `formatHeldBackDate()`, used by the version picker to render a held-back release's eligibility instant as a localized date
- `versionUtils.ts` — `getUpdateType()` classifies semver diff as `patch` | `minor` | `breaking` | `none` over the `shared` version grammar; the current side is classified by its exact version or, for a range (`>=1.2.3 <2.0.0`, `1.2.3 || 2.0.0`), by its base version; an `npm:` alias dependency through the spec it points at, and an alias as `latest` is never a version
- `logger.ts` — `Logger` singleton writing to VS Code output channel; use instead of `console.log`
- `notify.ts` — `showError()` helper
- `index.ts` — barrel exports for utils

### Shared (`src/shared/`)
Bottom layer: imports only Node built-ins — never `vscode` or another subsystem — so every subsystem, `tools` included, can import it through `src/shared/index.ts`. Files are named by meaning, never `utils.ts`/`helpers.ts`/`common.ts`.
- `guards.ts` — `isRecord()` (non-null, non-array object), `asString()`, `readRequiredString()` (non-blank string or `undefined`), `hasExactKeys()` (order-independent own-key match)
- `compare.ts` — `compareCodeUnits()` provides deterministic string ordering; `uniqueStrings()` preserves distinct values in first-seen order
- `crypto.ts` — `sha256Hex()` returns the lowercase SHA-256 digest of bytes or a string's UTF-8 encoding
- `errors.ts` — `describeError()` (an `Error`'s message, otherwise `String(value)`) and `describeStderr()` (`; stderr: …` suffix, empty for blank stderr)
- `fs.ts` — `hasErrorCode()`, `readOptionalFile()` (returns `undefined` only for `ENOENT`), and lexical `isPathWithin()`
- `ids.ts` — `COMMAND_IDS`, `VIEW_IDS`, `CONTEXT_KEYS`, and `CONTEXT_VALUE_TOKENS` are the shared command, view, context-key, and tree-token registries
- `text.ts` — the single text sanitizer and secret redactor: `sanitizeMultilineText()` (ANSI escapes and control characters stripped, line breaks normalized to LF, tabs to spaces; used by the logger), `sanitizeInlineText()` (single-line surfaces: controls and line-break runs become spaces, cut to 240 characters by default; used by tree items, audit report and conflict messages), and `redactCredentials()` (URL user info, `Authorization` values, credential assignments in plain, quoted and JSON form, npm tokens; generic `token`/`api-key` values are masked from a minimum length, 16 by default, and trailing `)`/`]` stay outside the masked value)
- `settingValues.ts` — the vscode-free knowledge behind `nestro.*` settings: `UPDATE_TARGETS`, `FILTER_TYPES` (with `isUpdateTarget()` / `isFilterType()`), the minimum release-age default and maximum, and `readMinimumReleaseAgeDays()` (a whole number in range is kept, anything else becomes the default); `config`, `providers` and `utils` import these instead of redefining them
- `versionGrammar.ts` — the single version/spec grammar: one anchored SemVer pattern behind `parseConcreteSemver()` / `isConcreteSemver()`, `parseVersionString()` (optional `workspace:` and comparator operator, then an exact SemVer; aliases, tags and compound ranges are `undefined`), `unwrapNpmAlias()`, `rangeBaseVersion()` (first comparator of a range's first `||` alternative, when an exact SemVer), `extractRangePrefix()` / `stripVersionDecorations()`, `isVersionOperand()` (the install-operand allowlist) and the `WORKSPACE_PROTOCOL` constant; read by `dependencySpec.ts`, `versionUtils.ts`, `packageTransforms.ts`, `registryClient.ts`, `pickVersion.ts` and `operandValidation.ts`
- `packageManagers.ts` — the package-manager table: `PACKAGE_MANAGERS` holds each manager's bin, lock files, install/add/remove verbs, dev flag, optional workspace-root flag (`removeNeedsWorkspaceRootFlag` when `remove` needs it too) and command dialect (audit argv, native metadata argv up to `--`, registry config file name), `YARN_DIALECTS` the Classic/Modern pairs; `PackageManager`, `DEFAULT_PACKAGE_MANAGER`, `LOCKFILES` in detection order (`LOCKFILE_PRIORITY`: pnpm, Yarn, Bun, npm), `NODE_MODULES_EXCLUDE_GLOB`, `isPackageManager()`, and `parsePackageManagerField()` (the single reader of a manifest `packageManager` field); adding a manager is one entry here plus its audit-schema parser
- `packageName.ts` — `classifyPackageName()` returns the first problem of a package-name operand (empty, leading hyphen, malformed scope, URL-unsafe scope or name) or `undefined`; `isValidPackageName()` is its boolean form for the metadata clients, `clients/operandValidation.ts` adds the localized messages
- `spawnTarget.ts` — `resolveSpawnTarget()` locates a Windows `.cmd` shim on `PATH` (never the working directory) and hosts it in the system `cmd.exe`, refusing any argument outside a metacharacter-free allowlist, while real `.exe` binaries and other platforms spawn directly; used by `processRunner.ts`, the Yarn version probe and `src/tools/auditSignaturesCli.ts`; `getWindowsSystemExecutablePath()` resolves `cmd.exe` and `taskkill.exe` from an absolute `SystemRoot` only
- `packagePresentation.ts` — the plain-data table for update icons/colors, dependency icons, filter colors, and the root label
- `index.ts` — barrel exports for shared

### Config (`src/config/`)
Typed `nestro.*` settings: the only place that calls `vscode.workspace.getConfiguration()`. Sits between `shared` and `utils` (it may import `vscode` and `shared`; `utils` reads settings, so it cannot sit above `utils`). Every `get*()` reads the setting live at call time and never caches; `SETTING_DEFAULTS` mirrors `contributes.configuration` in `package.json`, checked by `src/test/configurationManifest.unit.test.ts`.
- `settings.ts` — `SETTING_DEFAULTS`, one getter per setting, and `getUpdatePolicySettings()` (target, pre-release flag, minimum release age); an out-of-enum `updateTarget` / `defaultFilter` or an invalid `minimumReleaseAgeDays` falls back to the default
- `limits.ts` — every extension timeout, size and length limit (metadata, audit, `npm-check-updates` and Yarn probe processes, kill grace, update-cache TTL, watcher debounce, write-suppression release, view/notification/report text caps) defined once; limits that `src/tools` also needs live in `src/shared`, which `tools` may import (`INLINE_TEXT_MAX_LENGTH`)
- `index.ts` — barrel exports for config

### Tools (`src/tools/`)
Release/CI/VSIX tooling, isolated from `providers`/`utils`/`clients`/`commands` and allowed to import only the `src/shared` barrel (enforced by `src/test/importContract.unit.test.ts`); never bundled into the extension. Each CLI entry point runs as compiled JS from a `package.json` script that runs `test:compile` first — `node out/tools/<Name>Cli.js`.
- **VSIX packaging** — `vsixArchive.ts` reads a packaged `.vsix` and `vsixManifest.ts` its manifest `Identity` (dev-dependency `fast-xml-parser`, entity processing off and DOCTYPE/ENTITY rejected before parsing); `vsixPolicy.ts` layers the content policy over `vsixRules.ts` (allowlist, forbidden classes, source-path mapping), `vsixBundle.ts` (require-graph closure from the manifest entrypoint) and `vsixSecretScan.ts` (credential patterns), with the shared types in `vsixPolicyTypes.ts`; `extensionIdentity.ts` is the single parser of the `name`/`version`/`publisher` identity and checks the packaged manifests against the source one; `verifyVsix.ts` packages, evaluates and writes or deletes the artifacts (cleanup/lock error aggregation in `artifactCleanup.ts`), `verifyVsixRunner.ts` parses the arguments and reports the verdict, and `verifyVsixCli.ts` / `verifyVsixNodeIo.ts` are the Node bindings (`artifactDirectory.ts` containment, `artifactLock.ts` exclusive lock, `gitWorktree.ts`, `childProcess.ts`) driving `pnpm run check:vsce`; `artifactOutDir.ts` normalizes the `--out-dir` / `--artifact-dir` arguments every artifact CLI shares; the post-publish registry comparison is the stdlib-only `.github/scripts/release/compare-published.py` (budgets read from `.github/release-contract.json`), run by `compare-published.sh` and tested by `src/test/publishedArtifact.unit.test.ts`
- **Release** — `releaseContract.ts` loads `.github/release-contract.json` (strict schema: bundle member names and composition, `schemaVersions`, `candidateKeys`, artifact prefixes, workflow names, signer path, registry URLs, secret names, VSIX budget) and derives the member names, upload globs and size budgets the tools and policies below share; `releaseAnalyzer.ts` computes the next semantic-release version and changelog entry from commit history for `releasePrepare.ts` / `releasePrepareCli.ts` below; `releaseCandidate.ts` / `releaseCandidateCli.ts` and `releasePrepare.ts` / `releasePrepareCli.ts` build and validate the evidence `pnpm run release:candidate` / `release:prepare` produce; `releaseWorkflowPolicy.ts` checks the four release workflows against the contracts declared as data in `releasePrepareContract.ts`, `releaseCandidateContract.ts`, `releaseDispatchContract.ts` and `releasePublishContract.ts` (shared steps in `releaseWorkflowParts.ts`) through `workflowContract.ts`, and scans them for registry credentials outside the Open VSX publish step (rejected names such as `VSCE_PAT` nowhere); `releasePublishToolPolicy.ts` keeps `id-token` to the release `publish` job, pins the Marketplace OIDC publish steps, and checks the `.github/publish-tool/` manifest (root `@vscode/vsce` version) and lockfile (npmjs `resolved`, `sha512` integrity) for `ci:policy`
- **CI / supply-chain evidence** — `evidenceFiles.ts` is the single parser of `evidence.json` and the single reader/formatter of the `<sha256>  <file>` digest sidecar, and `normalizedManifest.ts` the single writer/parser of the normalized VSIX manifest (the Python copy in `compare-published.py` stays and must match its format); `ciEvidence.ts` / `ciEvidenceCli.ts` record `pnpm run ci:evidence` output; `ciPolicy.ts` / `ciPolicyCli.ts` validate the repository's CI workflow, CODEOWNERS, Dependabot configuration, and publishing tool files for `pnpm run ci:policy`, reading every action pin from `.github/reviewed-actions.json` through `reviewedActions.ts` (strict schema; a malformed registry is a violation, and every action entry must be used by some workflow); `ciWorkflowContract.ts` declares the reviewed `ci.yml` as data (header, jobs, step names and exact `run` text, `uses` as registry locators) and `workflowContract.ts` is the reusable checker that compares a parsed workflow with such a contract; `workflowYaml.ts` is the single strict YAML loader (unique keys, no anchors or aliases) and `workflowActionPolicy.ts` checks every `uses`/`run` of every workflow against the registry; `auditDependencies.ts` / `auditDependenciesCli.ts` gate `pnpm run audit:dependencies` (production advisories block at moderate, any advisory at critical, the rest are warnings); `auditSignatures.ts` / `auditSignaturesCli.ts` verify pnpm package signatures for `pnpm run audit:signatures`; `artifactSbom.ts` and `artifactProvenance.ts` (field validators in `artifactFields.ts`, SBOM inputs read from the archive by `packagedRuntime.ts`) build and verify the SBOM/provenance documents, `artifactProvenanceCli.ts` writes them for `pnpm run release:provenance`, and `evidenceBundle.ts` is the single verifier of a downloaded evidence bundle (digest, sidecar, manifest, SBOM, provenance) shared by `releaseCandidateCli.ts` and the packaged smoke

## Conventions
- Command IDs: `nestro.<camelCase>` — add to `COMMAND_IDS` (`src/shared/ids.ts`, with `VIEW_IDS`, `CONTEXT_KEYS`, `CONTEXT_VALUE_TOKENS`), declare in `package.json` `contributes.commands` with a `commandPalette` override (or list it palette-visible in `src/test/idsManifest.unit.test.ts`) **and** register in `activate()`; that test fails on any drift between the registry and the manifest
- TypeScript: strict mode — no `any`, explicit return types on exported functions
- Code comments: one line by default, three at most; English, present tense; they say what the code is, not how it came to be. No task/audit ids (`AUD-09`, `ARC-01`), no benchmark tables, no rationale essays — that context belongs in the commit message. Rules and examples: **[CODESTYLE.md](CODESTYLE.md)** → Code Comments
- Disposables: always `context.subscriptions.push(...)` — never leak event listeners or providers
- Imports: `import * as vscode from 'vscode'` (namespace import, not default)
- Import another subsystem only through its barrel `index.ts`, never through its implementation files; siblings inside one subsystem import each other directly. Barrels use selective named exports on subsystem boundaries, not `export *`; the enforceable layer order and its allowlisted exceptions are in **[CODESTYLE.md](CODESTYLE.md)** → Module Structure & Barrels, checked by `src/test/importContract.unit.test.ts`
- Module size and responsibility — no Swiss-army files: one responsibility per file, named after what it does (never `utils.ts`/`helpers.ts`/`common.ts`); product files ≤ 300 lines and functions ≤ 60, test files ≤ 800, enforced by ESLint (`max-lines`, `max-lines-per-function`) with no per-file exceptions. Extract identical code or knowledge on the second copy, similar logic on the third; no mode-flag abstractions; cross-subsystem code goes to `src/shared/` by meaning. SHAs, budgets, ids, defaults and limits live in registries; scripts live in files, never in strings. Full rules: **[CODESTYLE.md](CODESTYLE.md)** → Module Size & Responsibility
- `CHANGELOG.md` is generated by `@semantic-release/changelog` from commit messages — do not hand-edit release sections
- Full codestyle reference: **[CODESTYLE.md](CODESTYLE.md)**
- Accumulated project gotchas (tsdown, tsconfig, Vitest): **[LEARNINGS.md](LEARNINGS.md)**
- Release runbook (verified SHA and artifact identity, audits, environment approval, post-publish comparison): **[RELEASING.md](RELEASING.md)**
- README screenshots: **[images/SCREENSHOTS.md](images/SCREENSHOTS.md)** documents how the sidebar frames are captured and reproduced; `scripts/screenshots/` (`pnpm run screenshots`) automates the capture

## Commit Message Format

`conventionalcommits` preset — drives `semantic-release` and `CHANGELOG.md`. Format: `<type>(<scope>): <subject>`

| Type | Meaning | Bump | Release notes section |
|------|---------|:----:|---|
| `feat` | New user-facing feature | minor | Features |
| `fix` | Bug fix | patch | Bug Fixes |
| `part` | Partial fix / partial feature | patch | Bug Fixes |
| `perf` | Performance improvement | patch | Performance |
| `revert` | Revert of a previous commit | patch | Reverts |
| `refactor` | Refactoring, no behavior change | patch | Maintenance |
| `refactoring` | Refactoring, no behavior change | patch | Maintenance |
| `service` | Service / infrastructure change | patch | Maintenance |
| `style` | Visual / UI-only change | patch | Maintenance |
| `chore` | Tooling, deps, config | patch | Maintenance |
| `spark` | Small self-contained change | patch | Small changes |
| `docs` | Documentation only | — | — |
| `test` | Tests only | — | — |
| `ci` | CI / workflow only | — | — |
| `ghost` | Internal change, no release | — | — |

Every type in this table is active and may be used in new commits. Types with no bump produce no release and no changelog entry — never mark a `docs`, `test`, `ci` or `ghost` commit as changelog-bearing.

Scope examples: `toolbar`, `audit`, `picker`, `provider`, `deps`.

AI mirrors every `CLAUDE.md` edit into `AGENTS.md` in the same change; other agent-configuration synchronization is the owner's, and AI never runs synchronization commands before commits.
